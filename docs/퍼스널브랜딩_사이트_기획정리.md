- 목표 직군: **UX/UI 디자이너** (프론트엔드 개발자 아님)

## 3. AI 기능 (시그니처)

### 채택: "나에 대해 물어보세요" AI 챗봇

- 방문자(면접관)가 "React 경험 있어요?", "협업 스타일은?" 등을 물으면 이력·프로젝트 데이터를 컨텍스트로 가진 AI가 답변
- 프레이밍: 기술 과시가 아니라 **"대화형 경험을 설계한 디자인 작업물"**
  - 빈 입력창의 심리적 부담 → 추천 질문 칩으로 해소
  - 답변 톤을 내 브랜드에 맞게 설계
  - 답변에서 관련 작업물로 연결되는 플로우
  - → 이 UX 의사결정들 자체를 미니 케이스 스터디로 문서화 가능
- 위치: 첫인상은 Hero 비주얼이 잡고, 챗봇은 **정교하게 디자인된 플로팅 위젯 + About 근처에서 한 번 소개**
- 위젯 위치 확정: **오른쪽 하단** (채팅 위젯 관습 → 학습 비용 없음). Robin의 왼쪽 하단 상주 요소(영상 프리뷰)와 좌우가 바뀐 구도 — 오른쪽 하단은 챗봇 전용으로 비워두고, "맨 위로" 등 보조 요소는 왼쪽 하단으로

### 코너/여백 원칙 (왼쪽 하단 등)
- **코너를 채우기 위한 요소는 만들지 않는다.** 여백은 미완성이 아니라 디자인
- Robin의 왼쪽 하단 영상 프리뷰는 그의 미니멀 홈 구조가 만든 필요 — 우리는 Works 카드가 직접 노출되므로 프리뷰 역할이 이미 카드 안에 있음 (코너에 또 두면 중복)
- 프리뷰 욕심이 있다면: **카드 호버 시 화면 녹화 루프 재생** (`<video>` 태그로 가능, WebGL 불필요)
- 그래도 허전하면: 가벼운 상주 정보 **한 줄만** — `Open to work · Seoul` 상태 표시 or Hero 스크롤 힌트. 두세 개 쌓으면 잡동사니
- 추천 조합: 카드 호버 프리뷰 + Hero에만 상태 한 줄, 나머지 여백 유지
- 최종 판단은 시안 단계에서 실제 콘텐츠 넣고 눈으로 보고 결정 (지금 확정 사안 아님)
- Robin Noguier에게 WebGL이 정체성 증명이었듯, 나에게는 AI 챗봇이 그 역할

### 챗봇 역할 정의
> **"내가 자리에 없을 때 나 대신 면접관을 응대하는 사람"** — 면접관이 궁금해할 것을 대신 답하고, 다음 행동으로 안내

#### 필수 기능 (몸통)
1. **나에 대한 Q&A** — 경력·프로젝트·디자인 철학·협업 스타일 질문에 답변
   - 답변 재료는 **미리 작성한 지식 문서("김종욱 소개서")로 한정** — AI가 지어내지 않게
   - 지식 문서에 없는 질문 → "그건 직접 물어봐 주세요"로 응답하게 설계
   - 지식 문서는 케이스 스터디 콘텐츠에서 추출 (로드맵 1단계가 챗봇 재료 준비 겸함)
2. **작업물 안내 (내비게이터)** — 답변이 항상 관련 케이스 스터디 링크/스크롤로 연결
   - 예: "앱 디자인 해봤어요?" → GOI 소개 + 해당 페이지 링크
   - 챗봇 = 포폴을 더 깊이 보게 만드는 장치 (도슨트 아이디어를 이 방식으로 흡수)
3. **추천 질문 칩** — 빈 입력창 부담 해소, 클릭 한 번으로 대화 시작
   - 첫 칩 3~4개 + 대화 중에도 후속 추천 질문 계속 제시
   - 칩 문구 설계 자체가 UX 라이팅 작업물

#### 확장 기능 (필수 3개 완성 후)
4. **연락으로 연결 (클로징)** — 대화가 무르익으면 이메일/이력서 다운로드로 유도
5. **채용공고(JD) 매칭 + 추천** — 면접관이 채용공고를 붙여넣으면:
   - **왜 나를 뽑아야 하는지**: JD 요구사항 중 나와 맞는 부분을 항목별로 매칭해 설명
   - **뭘 보면 되는지**: 그 근거가 되는 웹/앱 프로젝트를 추천 — "○○ 역량을 보시려면 일광전구 케이스 스터디의 △△ 부분을 보세요" 식으로 구체적 위치까지 안내
   - 매칭 → 근거 작업물 → 연락 유도까지 이어지는 풀 퍼널
   - 과장 금지: JD와 안 맞는 부분은 솔직하게 "이 부분은 경험이 없지만 ○○로 배우고 있다" 식으로

#### 담당하지 말아야 할 것
- **범용 AI 노릇** — 무관한 요청("코드 짜줘" 등)은 정중히 거절. 범위가 넓어지면 정체성이 흐려지고 API 비용만 샘
- **사이트 본체의 대체** — 챗봇 없이도 포폴이 완결돼야 함. 챗봇은 보조 경로
- **과장** — 신입의 솔직한 톤 유지. 면접에서 들통날 말을 챗봇이 하면 안 됨

#### 부산물
설계 결정들(지식 범위 한정, 거절 설계, 칩 문구, 연결 플로우) 기록 → 그대로 "AI 챗봇 UX 설계" 미니 케이스 스터디가 됨

### 기타 아이디어 (보류)
- 관람 모드 전환 (채용담당자/개발자/구경꾼별 톤 변경)
- AI 도슨트 → 필수 기능 2번(내비게이터)에 흡수됨

### 구현 구조 (중요)
- 정적 사이트에 API 키를 노출하면 안 됨 → **Vercel 서버리스 함수** 경유
- 프론트에서 `/api/chat` 호출 → 함수 안에서 Claude API 호출
- 간단한 요청 횟수 제한(rate limit) 필수

```

├── index.html          ← 원페이지 (Hero~Contact)
├── projects/           ← 케이스 스터디 상세

```

## 4. 케이스 스터디란

- 결과물 이미지 나열이 아니라 **"결과물이 나오기까지의 과정과 이유를 이야기로 푼 것"**
- 면접관이 요구하는 이유: 완성 이미지만으론 스스로 생각한 건지 베낀 건지 구분 불가. "왜 이 색? 왜 이 구조?"에 답할 수 있음을 증명 = 실무의 설득 능력 검증

### 표준 뼈대
1. **개요** — 무슨 프로젝트, 내 역할, 기간 (3줄 이내)
2. **문제 정의** — 뭐가 문제였고 누구를 위한 디자인인가
3. **과정** — 리서치, 구조 설계, 와이어프레임
4. **디자인 결정** — 핵심 화면 몇 개 놓고 "왜 이렇게 했는가" ← 심장
5. **결과 + 회고** — 최종 결과물, 배운 것, 아쉬운 것

⚠️ 흔한 실수: 페르소나·저니맵 등 템플릿 산출물을 기계적으로 다 넣기. **핵심 결정 2~3개를 깊게**가 산출물 10개 나열보다 강함

### 기획서 장표와의 관계
- 형식으로서 장표(PDF/슬라이드)는 OK — 한국 UX/UI 신입 포폴은 PDF 장표가 대세
- 단, 기획서 ≠ 케이스 스터디:

| | 기획서 | 케이스 스터디 |
|---|---|---|
| 시점 | "이렇게 만들 겁니다" (미래형) | "이렇게 만들었고, 이유는" (과거형) |
| 설득 대상 | 팀원, 클라이언트 | 면접관 |
| 증명하려는 것 | 프로젝트의 타당성 | **내가 쓸만한 디자이너다** |

- 기획서 장표를 **재료로 재편집**: 문제 정의·구조 설계는 추려 오고 + ①최종 디자인 결과물 ②화면별 "왜" 설명 ③회고를 새로 붙임
- **장표 PDF가 본편, 웹사이트는 예고편** — 웹은 하이라이트만 보여주고 상세는 PDF로 연결

## 6. Robin Noguier 사이트 상세 분석 (메인 레퍼런스)

2020년 Awwwards SOTD + FWA + CSS Design Awards + Webby 수상작.

### 핵심 철학
> "포트폴리오의 목적은 케이스 스터디로 이끄는 것. 케이스 스터디는 '텍스트 없음(맥락 없음)'과 '텍스트 과다' 사이 균형을 찾는 데 가장 오래 걸렸다"

홈의 화려함은 미끼, **본체는 케이스 스터디**.

### 구조 — 극단적으로 단순
```
Home (WebGL 프로젝트 갤러리) ─── 케이스 스터디 × N
        └── About (메뉴는 이거 하나뿐)
```
- Skills·서비스·블로그 없음. 방문자의 행동은 "작업물 보기"와 "사람 알아보기" 둘뿐
- Hero 문구: "The designer you didn't know you needed.. until today" (자기소개 대신 위트)

### 케이스 스터디 구조 (Ueno 편 분석)
