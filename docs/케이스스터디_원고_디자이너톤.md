# 케이스 스터디 원고 정리 — 디자이너 톤 수정안

> 대상: `work-wrun.html` · `work-ilkw.html` · `work-goi.html` · `work-inns.html`
> 목표: "개발도 하는 사람"이 아니라 **"AI를 활용해 디자인을 끝까지 실현하는 디자이너"**로 읽히게.
> 각 프로젝트마다 **현재 원고 → 수정안 → 메모** 순서.

---

## 0. 톤 바꾸는 원칙

**지금 원고가 개발자처럼 읽히는 이유**
- 문장의 주어가 "무엇을 구현했다"에 쏠려 있음 — 왜 그렇게 디자인했는지(사용자·경험)가 뒤로 밀림
- 개발 용어가 그대로 노출됨: 서버리스 함수, 엔드포인트, React 컴포넌트 구조, PWA, JSON, clamp, max-width 컨테이너, 라이브러리 없이 …
- 상단 메타가 기술 스택(React · Vite · GSAP …)으로 시작함 — 첫인상이 개발 포트폴리오

**바꾸는 방향**
1. **문제 → 디자인 판단 → 결과** 순서로. 만드는 과정은 "AI를 활용해 직접 실현했다"는 무게로.
2. AI는 일을 대신한 존재가 아니라 **내가 활용한 도구**. 문장은 항상 "AI 어시스턴트를 활용해 ~했습니다" 형태로, 판단과 결정의 주어는 나.
3. 도구 이름 통일
   - 본문: 코드·리서치 쪽은 **AI 어시스턴트**, 이미지 쪽은 **AI 이미지 툴** (제품명 쓰지 않음)
   - 메타 줄: `AI Assistant` (Claude Code 대신). Midjourney는 디자이너 툴로 통용돼 메타에만 남김
4. 메타 첫 줄은 **역할**, 둘째 줄은 **도구**. 기술 스택은 뺌.
5. 숫자·사실(기간, 팀 규모, 화면 수, 휴리스틱 점검)은 그대로 — 신뢰의 근거.

**용어 바꾸기 표**

| 지금 | 디자이너 톤 |
|---|---|
| 서버리스 함수 · 엔드포인트 · API 키 노출 방지 | 실제 서비스처럼 안전하게 운영되는 조건까지 챙김 |
| React 컴포넌트 구조로 재구축 | 화면이 늘어나자 구조를 다시 설계 |
| PWA 구성 | 홈 화면에 설치해 앱처럼 쓰도록 |
| JSON 디자인 토큰 → CSS 변수 · Tailwind | 디자인 토큰으로 기준을 먼저 세우고, 시안과 실제 화면에 똑같이 적용 |
| clamp로 반응형 | 화면 크기에 따라 글자·여백이 자연스럽게 변하도록 |
| max-width 컨테이너 기준 | 화면 폭 기준 |
| 라이브러리 없이 스크롤 진행도 계산 | (빼기 — 결과인 "연출"만 말하기) |
| 구현했습니다 / 개발했습니다 | AI 어시스턴트를 활용해 실제 화면으로 옮겼습니다 |

## 1. W:RUN — 러닝 팬덤 앱 (팀)

### 메타 (히어로 아래 3줄)
**현재**
> React · TypeScript · Tailwind CSS / Claude API · Vercel 배포 / 2026.07 · 3주 · 6인 팀

**수정안**
> UX/UI Design · Brand Tone · AI Prototyping / Figma · Illustrator · Midjourney · AI Assistant / 2026.07 · 3주 · 6인 팀

### 01 — Overview
**현재**
> **A fandom app for runners.**
> 혼자 뛰는 사람들을 이어 주는 앱을 만들었습니다. 대회 정보를 추천하고, GPS로 그림을 그리는 코스를 제안하고, 함께 뛸 크루를 찾아 줍니다. 저는 UI 디자인과 프론트엔드 구현을 맡았고, 팀 안에서는 발표와 코딩 총괄, GitHub 협업 관리를 담당했습니다.

**수정안**
> **A fandom app for runners.**
> 혼자 뛰는 러너들을 하나의 팬덤으로 묶는 앱입니다. 대회 추천, GPS로 그림을 그리는 코스, 함께 뛸 크루 찾기까지 '같이 달리는 경험'을 중심에 두고 화면을 설계했습니다. 저는 앱 컨셉 정의와 전체 UI 디자인, 형광 라임을 중심으로 한 브랜드 톤을 맡았고, AI 어시스턴트를 활용해 디자인을 실제 화면까지 옮기며 팀 협업 관리도 함께 이끌었습니다.

### Challenge & Solution
**현재**
> **The first time I connected real APIs.**
> 가장 애를 먹은 지점은 API 연동이었습니다. … API 키가 브라우저에 노출되지 않도록 서버리스 함수를 두고, 프론트는 자체 엔드포인트만 호출하도록 분리했습니다. 요청 수와 대화 길이에 상한을 두어 비용이 새지 않도록 방어했습니다. …

**수정안**
> **Designing past the mockup, into a working product.**
> 러닝 앱은 챗봇, 지도, 음악, 순위 추천처럼 화면 밖의 기능과 맞물려야 비로소 경험이 완성됩니다. 시안에서 멈추면 '같이 달리는 느낌'이 실제로 전달되는지 확인할 수 없다고 판단했습니다.
>
> 익숙하지 않은 영역은 AI 어시스턴트를 활용해 풀어 갔습니다. 무엇부터 확인해야 하는지 질문을 잘게 나눠 리서치하고, 디자인 의도가 실제 동작에서도 유지되는지 하나씩 확인하며 대화형 러닝 코치 화면까지 완성했습니다. 실제 서비스처럼 안전하게 운영되는 조건도 놓치지 않았습니다.
>
> 3주 일정 중 2주 만에 핵심 흐름을 완성했고, 남은 1주는 인터랙션과 화면 디테일을 다듬는 데 썼습니다.

### What I Learned
**현재**
> **Tools got faster because I did.**
> GOI에서 구현하는 능력과 AI 활용법을 얻었고, 일광전구에서 팀 협업의 문제를 다루는 법을 배웠습니다. … 무엇부터 확인해야 하는지 아는 것이, 결국 도구를 쓸 수 있게 만들었습니다.

**수정안**
> **AI moved faster once I knew what to ask.**
> GOI에서 혼자 끝까지 만드는 법을, ILKW에서 팀이 같은 기준으로 움직이는 법을 배웠고, W:RUN은 그 두 경험이 합쳐진 프로젝트입니다.
>
> AI를 활용하면서 디자이너가 정한 방향을 훨씬 빠르게 검증하고 형태로 만들 수 있었습니다. 다만 무엇을 만들지, 어디까지가 좋은 경험인지 정하는 것은 여전히 디자이너의 몫이라는 걸 이 프로젝트에서 확인했습니다.

**메모**
- 서버리스·엔드포인트·비용 방어는 "안전하게 운영되는 조건" 한 문장으로 줄임. 면접에서 물어보면 그때 자세히 말하면 됨.

## 2. ILKW — 일광전구 웹 리뉴얼 (팀)

### 메타
**현재**
> React · Vite · GSAP · Three.js / 2026.06.05 — 07.02 · 팀 프로젝트 / UI Design · Frontend · Usability Test

**수정안**
> UI Design · Design System · Usability Test / Figma · Illustrator · Photoshop · Midjourney · AI Assistant / 2026.06.05 — 07.02 · 팀 프로젝트

### 01 — Overview
**현재**
> **A brand experience, not a product list.**
> 제품 판매몰이던 일광전구 웹사이트를 브랜드 경험 중심의 인터랙티브 웹으로 리뉴얼했습니다. 저는 UI 디자인과 프론트엔드 구현, 사용성 평가를 맡았습니다. 브랜드의 인상을 화면 전반에서 일관되게 전달하는 것을 목표로 했습니다.

**수정안**
> **A brand experience, not a product list.**
> 제품을 나열하던 일광전구 쇼핑몰을, 브랜드의 분위기를 먼저 경험하는 인터랙티브 웹으로 리뉴얼했습니다. 저는 UI 디자인과 사용성 평가를 맡았고, AI 어시스턴트를 활용해 디자인 의도가 실제 화면에서도 그대로 전달되도록 만드는 과정까지 함께했습니다. 목표는 어느 화면에서든 같은 브랜드의 인상이 느껴지게 하는 것이었습니다.

### Challenge & Solution
**현재**
> **Consistency had to be designed into the team.**
> 첫 팀 프로젝트에서는 각자 디자인을 잘해도 구현 단계에서 스타일의 통일성이 쉽게 무너졌습니다. … Git 협업 가이드를 만들어 … 반응형 레이아웃은 max-width 컨테이너 기준을 다시 세워 안정화했습니다. …

**수정안**
> **Consistency had to be designed into the team.**
> 여러 명이 나눠 디자인하다 보니, 각자의 화면은 좋아도 한 사이트로 모았을 때 통일감이 무너졌습니다. 1차 사용성 점검에서는 메뉴가 동작하지 않거나 화면이 옆으로 밀리고, 모바일에서 글이 잘 읽히지 않는 문제도 드러났습니다.
>
> 브랜드 무드는 AI 이미지 툴을 활용해 여러 방향의 비주얼을 빠르게 만들어 팀과 먼저 합의했습니다. 이어서 타이포·컬러·간격을 디자인 토큰으로 정리해 팀 전체가 같은 기준으로 화면을 만들 수 있게 했고, 작업 방식을 맞추기 위한 협업 가이드도 제안해 합의했습니다.
>
> 이후 닐슨의 10가지 사용성 원칙을 기준으로 점검 → 개선 → 재점검을 반복했고, 화면 폭 기준을 다시 세워 기기마다 흐트러지던 레이아웃을 바로잡았습니다.

### What I Learned
**현재**
> **A shared rule can make a team move faster.**
> 처음 해 본 Git 협업과 팀 단위 구현에서, 문제를 개인의 숙련도로만 해결하려 하면 반복해서 같은 비용이 생긴다는 것을 알았습니다. …

**수정안**
> **A shared rule can make a team move faster.**
> 문제를 각자의 실력으로만 메우면, 같은 수정이 계속 반복된다는 것을 첫 팀 작업에서 겪었습니다.
>
> 디자인 토큰과 협업 가이드는 문서가 아니라 팀이 같은 판단을 내리게 하는 기준이었습니다. 좋은 화면 하나를 그리는 것만큼, 모두가 좋은 화면을 만들 수 있는 규칙을 설계하는 것도 디자이너의 일이라는 걸 배웠습니다.

## 3. GOI — 다이어리 앱 (개인)

### 메타
**현재**
> React · Vite · PWA / 2026.03.24 — 06.01 · 개인 프로젝트 / Planning · Design · Development

**수정안**
> Product Design · UX Planning · AI Prototyping / Figma · AI Assistant / 2026.03.24 — 06.01 · 개인 프로젝트

### 01 — Overview
**현재**
> **A diary app made for one focused step at a time.**
> GOI는 기록하는 경험을 더 가볍고 개인적으로 만들기 위해 기획한 다이어리 앱입니다. 기획, 사용자 플로우, UI 디자인, 개발과 배포까지 전 과정을 혼자 진행했습니다. 온보딩·홈·작성·캘린더·친구·상점 등 16개 화면을 설계하고 구현했습니다.

**수정안**
> **A diary app made for one focused step at a time.**
> 기록을 더 가볍고 나다운 경험으로 만들기 위해 기획한 다이어리 앱입니다. 서비스 기획과 사용자 흐름 설계, UI 디자인을 혼자 진행했고, AI 어시스턴트를 활용해 실제로 쓸 수 있는 앱으로 배포하기까지 마무리했습니다. 온보딩부터 작성·캘린더·친구·상점까지 16개 화면을 설계했습니다.

### Challenge & Solution
**현재**
> **I rebuilt the idea as a product, not just a screen.**
> 첫 개인 프로젝트였고 React에 익숙하지 않은 상태에서 … React 컴포넌트 구조로 다시 구축했습니다. 일기 생성 흐름은 … 4장의 카드로 나눠 … PWA를 구성해 … AI 생성 기능은 … 프로토타입입니다. …

**수정안**
> **I turned a blank page into four small questions.**
> 일기를 쓰려고 할 때 가장 먼저 막히는 건 빈 화면이라고 봤습니다. 그래서 일기를 만드는 과정을 제목, 컨셉, 꼭 넣을 문구, 추가 요청의 4장 카드로 나눠, 한 번에 하나의 질문에만 답하면 되도록 설계했습니다.
>
> 이 흐름이 실제 손에서 어떻게 느껴지는지 확인하려고, AI 어시스턴트를 활용해 직접 동작하는 앱으로 만들었습니다. 화면이 늘어나자 구조를 처음부터 다시 설계했고, 홈 화면에 설치해 앱처럼 쓸 수 있게 했습니다.
>
> AI 일기 생성 기능은 화면과 사용 흐름까지 설계한 프로토타입 단계이며, 실제 생성 모델 연동은 하지 않았습니다. 완성도를 있는 그대로 보여주는 것이 맞다고 판단했습니다.

### What I Learned
**현재**
> **Building it taught me how to make decisions.**
> 혼자 끝까지 만들어 보며 화면을 설계하는 것과 실제로 동작하는 제품을 만드는 것 사이의 차이를 배웠습니다. …

**수정안**
> **Building it taught me how to make decisions.**
> 혼자 끝까지 만들며, 보기 좋은 화면과 실제로 쓰이는 제품 사이의 거리를 체감했습니다. 모르는 영역 앞에서도 AI 어시스턴트를 활용해 질문을 나눠 묻고, 작은 단위로 확인하며 앞으로 나아가는 방법을 이때 익혔습니다.
>
> 여기서 얻은 실행력과 AI 활용 방식이 ILKW와 W:RUN으로 이어졌습니다. 지금 보면 고치고 싶은 부분도 보이지만, 그만큼 보는 기준이 생겼다는 뜻이라고 생각합니다.

**메모**
- Overview 리드("one focused step")와 겹치지 않게 Challenge 리드를 바꿈.
- AI 일기 생성이 프로토타입이라는 정직한 문단은 그대로 유지 — 신뢰 포인트.

**수정안**

### 01 — Overview
**현재**
> **A brand site that starts where the ingredients grow.**
> … 기획, Figma 시안, 디자인 토큰 정리, 퍼블리싱과 배포까지 혼자 진행했습니다. …

**수정안**
> **A brand site that starts where the ingredients grow.**
> 이니스프리 브랜드 웹사이트를 '제주에서 찾은 성분'이라는 하나의 이야기로 다시 구성한 리뉴얼 시안입니다. 기획과 Figma 시안, 디자인 시스템 정리를 혼자 진행했고, AI 어시스턴트를 활용해 실제 사이트 배포까지 마무리했습니다. 히어로 영상, 브랜드 철학, 제주 원료 지도, 성분 스토리, 제품, 지속가능성까지 7개 장면으로 이어지는 원페이지로 설계했습니다.

### Challenge & Solution
**현재**
> **I let the ingredients lead, and the products follow.**
> (1문단 그대로) … 라이브러리 없이 스크롤 위치로 진행도를 계산했고 … JSON 디자인 토큰 … CSS 변수와 Tailwind 설정 … clamp …

**수정안**
> **I let the ingredients lead, and the products follow.**
> 화장품 브랜드 사이트는 대부분 신제품과 프로모션이 먼저 보이는 구조라, 이니스프리가 가진 '제주'라는 강점이 흐려져 있다고 봤습니다. 그래서 흐름을 브랜드 철학 → 원료 산지 → 성분 → 제품 순으로 바꿔, 성분이 왜 좋은지 먼저 이해한 뒤에 제품을 만나도록 설계했습니다.
>
> 핵심 장면인 Ingredient Story는 스크롤하는 동안 화면을 붙잡아 두고, 그린티·화산수·동백의 이미지와 이야기가 차례로 넘어가도록 연출했습니다. 제품 설명을 읽는 대신 성분을 '보는' 경험을 만들고 싶었습니다. 움직임에 민감한 사용자를 위해 기기의 '동작 줄이기' 설정도 존중했습니다.
>
> 레퍼런스 브랜드 페이지의 색·여백·폭을 실측해 디자인 토큰으로 먼저 정리하고, 그 기준을 Figma 시안과 실제 사이트에 똑같이 적용했습니다. 모바일부터 데스크톱까지 같은 리듬으로 보이도록, 화면 크기에 따라 글자와 여백이 자연스럽게 변하게 했습니다.
